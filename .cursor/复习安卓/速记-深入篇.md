# 深入篇速记

## Handler 源码层

为什么存在：UI 单线程。View 非线程安全，给每个 View 加锁会性能崩、还容易死锁。所以单线程 + 消息切换。

- Looper：ThreadLocal 保证一线程一份；再 prepare 会抛错。ThreadLocalMap 的 key 弱引用、value 强引用，线程池里用完必须 remove。
- Handler 构造：`Looper.myLooper()`，null 就抛「没 prepare」。
- MessageQueue：按 `when` 排序的单链表，不是真队列。`enqueueMessage` 有 synchronized，所以任意线程 send 都安全。
- `next()`：`nativePollOnce` = epoll_wait。-1 无限睡，0 立刻返回，>0 睡到点。延迟靠 epoll timeout，不是 timer。
- 同步屏障：`target==null` 的标记消息。`next()` 跳过同步，只取异步。ViewRootImpl 绘制前会插，保证 vsync 不被 App 消息堆住。**自己别乱插，忘了 remove 界面僵死。**
- IdleHandler：空闲才跑。true 保留，false 移除。
- dispatchMessage 优先级：msg.callback（post Runnable）→ Handler.Callback → handleMessage。
- quit 立刻清空；quitSafely 只扔未到期。主线程 Looper 不许 quit。
- HandlerThread：自带 Looper 的串行后台队列。`getLooper()` 会等 Looper 建好。

泄漏完整链：`MessageQueue → Message.target → Handler → Activity`。还有 `view.postDelayed` 这条隐藏链。

## Service 深入

最大误解：Service ≠ 后台线程。它跑主线程。存在意义是**抬高进程优先级** + 给系统一个可调度的后台载体。

- `stopSelf()` 无条件停；`stopSelfResult(startId)` 后面还有更新的 startId 就不停（避免掐新任务）。
- 多次 bind：onBind 只一次，复用同一个 IBinder。混合启动要 stop + 全 unbind 才销毁。onUnbind 返回 true 下次走 onRebind。
- 启动走 AMS：反射 new Service → attach → onCreate → onStartCommand。bind 再走 onBind，AMS 回调客户端 `onServiceConnected`。跨进程拿到的是 BinderProxy。
- 8.0 后台限制；`startForegroundService` 后 5 秒内必须 `startForeground`。9 要 FOREGROUND_SERVICE 权限。12+ 后台启动前台服务受限。
- 对比：Service 是组件能抬优先级；Thread 只是执行单元；WorkManager 能被系统重调度。
- 保活只谈合规：前台通知、白名单、厂商推送、WorkManager。双进程/1 像素/无声音乐别主动讲。

坑：主线程耗时 ANR（前台 20s / 后台 200s）；忘 startForeground；bind 不解绑 Context 泄漏；onBind 返回 null 客户端卡住。

## ANR

本质：AMS 先埋延时炸弹，组件做完通过 Binder 拆弹；时限到了没拆就炸。完成通知也要排队进主线程，所以**超时那一刻主线程正在跑的方法就是元凶**。

| 类型 | 时限 |
|---|---|
| 输入分发 | 5s |
| 前台广播 | 10s |
| 后台广播 | 60s |
| 前台 Service | 20s |
| 后台 Service | 200s |
| Provider publish | 10s |

后台 ANR 常直接杀，不弹框。traces.txt 堆栈不一定是真凶，要配 CPU / iowait。

排查四步：logcat 搜 ANR in → traces 看 main 栈 → 看 CPU（自己高=死循环/GC；iowait 高=IO/SP；CPU 空闲=锁/Binder；整体高本进程低=被饿死）→ 对 AMS 时间点。

高频坑：主线程网络 / SP（`handlePause/Stop` 里 `QueuedWork.waitToFinish` 等 apply 落盘）/ 抢锁 / Binder 对端忙 / Provider.onCreate 比 Application 还早 / 主线程 `runBlocking`。

监控：Looper.setMessageLogging（BlockCanary）；Choreographer 掉帧；App 看门狗往主线程 post，超时 dump。

## OkHttp

`newCall` → RealCall。同步 execute；异步 enqueue 进 Dispatcher。

Dispatcher：maxRequests=64，maxRequestsPerHost=5。线程池像 CachedThreadPool，真正限流在 Dispatcher，超了进 readyAsyncCalls。

拦截器链（责任链递归 proceed）：

1. Application Interceptor（只一次，缓存命中也走）
2. RetryAndFollowUp
3. Bridge（补头、gzip）
4. Cache
5. Connect（连接池 / TCP / TLS）
6. Network Interceptor（每次真网络都走，缓存命中不走）
7. CallServer

连接池默认空闲 5 条、保活 5 分钟。HTTP/2 多路复用。默认没有 Cache，要自己 `cache()`。ResponseBody 必须关，否则连接泄漏。

## Retrofit

本质：动态代理封装 OkHttp，自己不发请求。注解运行时解析，ServiceMethod 有缓存。

- CallAdapter：怎么执行、返回啥（Call / Observable / suspend）。
- Converter：怎么序列化（Gson / Moshi）。
- suspend：多 Continuation 参数，内部 enqueue，回调 resume。

坑：`@Multipart+@Part`、`@Field+@FormUrlEncoded`、大文件加 `@Streaming`、`@Url` 覆盖 baseUrl、相对 path 别以 `/` 开头。

## 协程

三板斧：挂起=多 Continuation（CPS）· 编译器状态机 · Dispatcher 定线程。  
`delay` 挂起释放线程；`Thread.sleep` 阻塞线程。

结构化并发：父取消子全取消。viewModelScope / lifecycleScope 销毁自动收。  
SupervisorJob：子失败不影响父和兄弟。  
launch 异常立刻向上冒；async 要等 await 才抛。取消是协作式的，`while(true)` 不响应 cancel。  
`runBlocking` 阻塞线程，主线程别用；`coroutineScope` 挂起不阻塞。  
GlobalScope 不绑生命周期，别用。

Flow 冷流；StateFlow 热+必有初值；SharedFlow 事件型。`flowOn` 切上游。
