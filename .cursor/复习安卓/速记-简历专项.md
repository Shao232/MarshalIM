## 1. 事件分发（基础栏写了，必问）

一句话：事件从 Activity → DecorView 往下传，谁消费谁就停。

三个方法：

| 方法 | 谁有 | 干什么 |
|---|---|---|
| `dispatchTouchEvent` | Activity / ViewGroup / View | 分发入口 |
| `onInterceptTouchEvent` | **只有 ViewGroup** | 拦不拦，给自己 |
| `onTouchEvent` | 都能重写 | 自己吃不吃 |

流程（按下为例）：

1. Activity.dispatch → DecorView → 子 ViewGroup.dispatch
2. ViewGroup 先问 `onInterceptTouchEvent`：true = 自己处理，不再往下；false = 给子 View
3. 子 View `onTouchEvent` 返回 true = 消费；false = 回传给父

追问：

- **DOWN 被谁消费，后续 MOVE/UP 就找谁**（目标 View）。父想中途抢，要拦截，子会收到 `ACTION_CANCEL`。
- `onTouchListener` 优先于 `onTouchEvent`，返回 true 就进不了 onTouchEvent。
- 滑动冲突：外层不拦，留给能滑的孩子；或按方向，横向给 ViewPager、纵向给列表。

和绘制的关系：绘制决定长什么样，分发决定摸谁。简历把两句写一起，面试常连着问。

## 2. MVC / MVP / MVVM

一句话：差在 **View 和业务谁认识谁、数据怎么回到界面**。

### 先认同一套三层（你的理解对）

三种都是：

- **M（Model）**：数据。接口、数据库、缓存、解析。不管界面。
- **V（View）**：界面。按钮、列表、loading。不管「向谁要数据、怎么算」。
- **中间层**：调度。用户点了按钮，中间层去调 Model，再让界面更新。

你说的 MVC 就是这个：M 数据，V 是 Activity，C 是控制层，可以把 Activity 里的业务挪到 C。  
**这一步想法是对的。** Android 里真正的分歧是：这个「中间层」叫什么、它能不能直接握着 Activity。

| | MVC | MVP | MVVM |
|---|---|---|---|
| 谁当 View | Activity 既是 View 又常兼 Controller | Activity 只做 View | Activity 只做 View，更薄 |
| 中间层 | Controller 直接改 View、调 Model | Presenter 通过接口指挥 View | ViewModel **不持有 View** |
| 数据怎么回界面 | Controller 拿到结果自己 `setText` | Presenter 调 `view.showXxx()` | LiveData / Flow，View 观察 |
| 典型问题 | Activity 膨胀，啥都写里面 | 接口多，Presenter 握 View 要解绑 | 学习成本；LiveData 粘性事件 |

### MVC（最早）

Model 数据，View 展示，Controller 调度。  
Android 里 Activity 天然是 View，又常常把 Controller 写进去 → **Activity 又胖又难测**。旋转、泄漏都难收。

### MVP

把业务从 Activity 抽到 Presenter。View 变成接口（`showLoading` / `showList`）。  
Presenter 测起来方便，但 **Presenter 强持有 View**，`onDestroy` 必须 `detach`，否则泄漏。页面一多，接口爆炸。

### MVVM

ViewModel 只出状态，不认 Activity。页面 `observe` 数据变化再画。  
旋转后 ViewModel 还在，数据不丢。`onCleared()` 才真正清。  
这是 Jetpack 主推，也是简历上「熟悉 MVVM」时面试官默认的版本。

关系可以记成：

```
MVC：Activity 自己又当导演又上台
MVP：Presenter 拿着对讲机指挥舞台（必须记得放下对讲机）
MVVM：ViewModel 只改字幕牌，舞台自己看着牌演（不认识演员）
```

项目怎么说：样样有多数页面还是 Activity 里直接写（偏 MVC）。记账有 Room，可以往 MVVM 靠。**别说全项目标准 MVVM。**

### 怎么一眼区分（点同一个按钮）

用户点「刷新」，三种走法不一样：

**MVC**  
Activity 里的点击监听（它就是 C）→ 调 Model 拉数 → 回来自己 `textView.text = ...`。  
Android 里 C 经常没独立成类，就写在 Activity 里。你说「把 Activity 里的代码抽到控制层」——如果抽出去的 C **还是直接拿着控件改**，还是 MVC。

**MVP**  
Activity 只把「点了刷新」告诉 Presenter。Presenter 调 Model。回来 Presenter 调 `view.showList(data)`。  
Activity 实现这个接口去改控件。中间层**认识 View，主动指挥它**。

**MVVM**  
Activity 只把「点了刷新」告诉 ViewModel（`viewModel.refresh()`）。ViewModel 调 Model，结果塞进 `LiveData`。  
Activity 事先 `observe`，数据变了自己画。中间层**不认识 View，只改数据**。

判断口诀：

1. 中间层有没有直接 `setText` / 找控件？有 → MVC  
2. 中间层有没有握着 View 接口、喊 `showXxx`？有 → MVP  
3. 中间层只改 LiveData/State，页面自己观察？→ MVVM

### MVC 和 MVP 为啥像，差在哪一刀

都是「中间层调 Model，再让界面更新」，所以像。  
**差在中间层认不认具体的 Activity。**

- MVC 的 C：往往就是 Activity 自己，或一个类里直接握着 `TextView`。换个页面，C 要改。
- MVP 的 P：只认 View **接口**（`showList` / `showError`），不 import 任何控件。Activity 实现接口。换个 Fragment 实现同一套接口，Presenter 一行不用改。

没这层接口、中间层还能 `findViewById`，只是把代码挪了个文件，**还是 MVC**。  
有这层接口、Presenter 只喊 `view.showXxx()`，才是 MVP。

连带两个后果：Presenter 能单测（丢个假 View 进去）；Presenter 握着 View，Destroy 必须 detach。

追问：为啥现在更推 MVVM？  
View 和业务解耦、旋转不丢、配合 LiveData/Flow 生命周期安全；MVP 的 detach 和接口膨胀是老痛点。

## 3. ViewModel / LiveData / Binding

**ViewModel**  
活得比 Activity 配置变更长。旋转销毁重建，同一个 ViewModel 还在。真正清是 `onCleared()`（页面回退）。  
别往 ViewModel 里塞 Context / View / Activity。要 Context 用 `AndroidViewModel` 的 Application。

**LiveData**  
能感知生命周期，STOP 了不回调，避免更新死页面。  
`observeForever` 不跟生命周期，要自己 remove。

### LiveData 数据倒灌（粘性事件）

一句话：后订阅的人会立刻拿到**最后一条已经 set 过的值**，像把旧数据又灌回新页面。

**为啥会这样（源码就记两个数）**  
LiveData 里：`mVersion` 每 `setValue`/`postValue` 加一；每个观察者有自己的 `lastVersion`。  
`observe` 时新观察者的 `lastVersion = -1`。页面一回到 STARTED，`considerNotify` 发现 `-1 < mVersion`，就把**当前 value 再派发一次**。  
这是故意的：旋转后新 Activity 要立刻拿到最新列表，不用重新请求。  
**状态**该粘；**事件**（Toast、跳转、弹窗）不该粘。倒灌出在把事件当状态存。

**典型场景**

1. 登录成功 `liveData.value = true`，跳首页。旋转 / 返回再进，又 observe，又跳一次。
2. ViewPager 里 Fragment 先不可见后可见，又收到上一次的「去详情」。
3. 同一个 LiveData 两个观察者，第二个一注册就吃到旧值。

**怎么修（说得出 2 个就够）**

| 做法 | 要点 |
|---|---|
| **SingleLiveEvent** | 内部 AtomicBoolean，只有显式 set 后下一次才通知，后来的观察者不再吃旧值。多个观察者只有一个能收到。 |
| **Event 包装** | `Event<T>` 带 `hasBeenHandled`，用过一次标已消费。 |
| **版本号 / 钩子** | 自己记 lastVersion，相等就不处理。 |
| **SharedFlow** | `replay=0` 的 SharedFlow / Channel，事件不回放。现在更推荐。 |

判断：列表、用户信息 → 用普通 LiveData，就要粘。Toast、导航 → 别用普通 LiveData。

口述：

> LiveData 是粘性的，为的是配置变更后恢复状态。新观察者 lastVersion 是 -1，一订阅就收到最后一条。把跳转、Toast 放进去，页面重建就会倒灌。状态用 LiveData，事件用 SingleLiveEvent 或 SharedFlow。

**ViewBinding vs DataBinding**  
ViewBinding：只生成绑定类，找控件，没有 `@{ }`。  
DataBinding：还能在 xml 里绑变量、表达式，重、难查、编译慢。  
很多项目（包括本项目）只用 ViewBinding。

## 4. 组件化 + ARouter（对着样样有讲）

为什么拆：驾校、记账、玩安卓、题库各一个 module，app 壳只负责组装。改一块不用全编，人多也不抢一个工程。

ARouter：编译期注解生成路由表。`ARouter.getInstance().build(path).navigation()`。  
path 至少两级：`/ledger/home`。Activity 加 `@Route`，模块和壳都要 kapt。

必说的坑：

- 壳没 `implementation` 这个模块 → 点了没反应（记账就踩过）
- 没 `openDebug()` 时部分机型找不到路由
- 初始化要在 Application，要快；首屏用不到的别堵启动

传参：`withString` / `withParcelable`。跨模块拿接口用 `@Autowired` 或 Provider，别互相直接依赖。

## 5. Room / WorkManager

**Room**：SQLite 的一层。DAO + Entity，编译期生成实现。查询默认不能在主线程（会崩）。记账模块自己的库，别和宿主库混。

**WorkManager**：可推迟、要保证执行的任务（同步、上报）。进程死了系统会再调度。  
不是「后台线程」。要立刻、和界面绑着的用协程；要抬进程优先级用前台 Service；要保证做成用 WorkManager。

## 6. WebSocket 长连 + 重连

和 HTTP：HTTP 一次一问一答；WebSocket 握手后双工，服务端能推。

口述三件套：

1. 连上：鉴权、心跳（定时 ping，超时当断）
2. 断了：区分主动关还是网络挂；指数退避重连（1s、2s、4s，设上限），避免死循环打服务器
3. 回到前台 / 网络恢复再连；进后台可降心跳或断开（看业务）

没在项目里写完整重连，就说「了解策略，项目里推送走的是极光，不是自研长连」。有做再展开。

## 7. MMKV vs SP

SP：xml，整文件读写。`apply()` 看似异步，Activity `onPause/onStop` 时 `QueuedWork.waitToFinish()` 会等它落盘 → 大数据 ANR。  
MMKV：腾讯，mmap，按条写，适合高频 KV。

项目：启动里主线程先 `MMKV.initialize`，因为首屏可能读配置。

## 8. 启动优化（项目能举实例）

启动三段：Application.onCreate → 第一个 Activity → 首帧绘制。用户感知的是冷启动到第一帧。

原则：主线程只留**首屏马上要用的**。

项目实例（`MApplication`）：

- 主线程立刻：MMKV
- 主线程但可稍后：ARouter
- 丢到子线程：极光、Bugly（晚几秒收到推送、上报都能接受）

还能说：启动任务编排、懒加载、减少主线程 IO、ViewStub / 异步 inflate。别吹没做过的插件化、稳定版全量热修。

## 9. 泄漏清单 + LeakCanary

常见：Handler / 非静态内部类、单例握 Activity、监听没反注册、bind Service 没 unbind、静态 Context、WebView。

LeakCanary：debug 包自动看 Activity 是否该回收没回收，给引用链。线上还要看 Leak 上报，不能只靠它。
